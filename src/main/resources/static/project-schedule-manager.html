프로젝트 소개

AI 갓생비서는 일정 CRUD, 반복 일정, 만다라트 목표 관리, Claude 기반 AI 일정 추천 챗봇까지 갖춘 개인 스케줄링 백엔드 서비스입니다. JWT 액세스/리프레시 토큰 로테이션과 Redis 기반 캐싱·로그아웃 블랙리스트로 인증·성능 계층을 구성했고, 상태 변경은 폴링 대신 SSE로 실시간 반영합니다. AI 챗봇은 Spring AI(ChatClient)로 Claude를 연동해 구조화된 다중 일정 추천/수정 제안을 지속 대화 형태로 제공하며, pgvector 기반 RAG로 사용자의 만다라트 목표와 과거 일정을 반영한 개인화된 제안을 만듭니다. AWS(EC2 + RDS + ElastiCache)에 GitHub Actions로 CI/CD 파이프라인을 구성해 배포까지 직접 진행했습니다.

ACTION 실행
토큰 타입 구분 및 검증

JwtUtil에 tokenType claim(ACCESS/REFRESH)을 추가하고, JwtAuthenticationFilter가 ACCESS 타입만 인증에 사용하도록 검증해 리프레시 토큰이 Authorization 헤더로 재사용되는 것을 차단

Redis 기반 단일 세션 로테이션

리프레시 토큰을 refresh:{email} 키(TTL = 잔여 유효기간)로 저장, 재로그인 시 같은 키를 덮어써 이전 토큰을 자동 폐기. POST /api/auth/refresh는 서명·만료 검증과 Redis 저장값 일치를 모두 통과해야만 access/refresh를 함께 재발급해, 탈취된 토큰이 재사용되면 값 불일치로 즉시 감지

로그아웃 시 이중 무효화

액세스 토큰 블랙리스트 등록에 더해 refresh:{email} 키까지 함께 삭제해, 로그아웃 이후에는 재발급 경로 자체를 차단

프론트 자동 재발급 및 중복 호출 방지

401/403 응답 시 리프레시 토큰으로 한 번 재발급 후 재요청하고, 동시에 여러 요청이 만료를 맞아도 진행 중인 refresh Promise를 공유(refreshInFlight)해 재발급 호출이 중복되지 않도록 처리

운동, 영양제, 식단처럼 매번 반복되는 일정을 매번 손으로 새로 등록해야 하는 불편

TASK과제
변경 시점에만 갱신되는 실시간 구조

폴링 없이, 변경이 발생한 순간에만 프론트가 즉시 갱신되도록 전환

기존 기능을 재사용하는 반복 일정

규칙만 등록하면 이후 일정이 자동 생성되되, 보드/캘린더/자동 상태 전환/AI 추천 컨텍스트는 그대로 재사용 가능해야 함

ACTION실행
유저별 SSE 브로드캐스트 구성

ScheduleEventPublisher가 유저별 SseEmitter 목록을 관리하다가, 일정 생성/수정/삭제/자동 상태 전환 시점에 맞춰 해당 유저의 SSE 연결로 직접 이벤트를 전송(GET /api/schedules/stream)

인증 헤더 제약 및 재연결 처리

EventSource가 커스텀 헤더를 못 보내는 제약에 맞춰 이 경로에 한해 쿼리 파라미터 토큰을 허용하도록 예외 처리하고, 짧은 토큰 수명 때문에 재연결 시 토큰이 만료돼 있는 문제는 네이티브 자동 재연결 대신 onerror에서 직접 끊고 토큰을 새로 받아 재연결하도록 구현

서버 스케줄러 기반 반복 일정 생성

RecurringSchedule에 요일/시작·종료 시각/기간/카테고리 규칙만 등록하면 실제 Schedule 행을 앞으로 60일치 미리 생성, 매일 새벽 1시 스케줄러가 창을 다시 60일로 채워 무기한 반복도 끊기지 않게 유지. 생성된 occurrence는 평범한 Schedule이라 기존 보드/캘린더/AI 컨텍스트 로직을 그대로 재사용

01. Redis 캐시 직렬화 버그와 그 회귀

Redis Jackson
Resolved

Root Cause

GenericJackson2JsonRedisSerializer(ObjectMapper) 생성자가 기본(no-arg) 생성자와 달리 넘겨받은 ObjectMapper에 default typing을 활성화하지 않아, 캐시 히트 시 List<ScheduleResponseDto>가 List<LinkedHashMap>으로 역직렬화됨. DTO 필드에 타입으로 접근하는 AiService가 이를 처음 노출시켰다(ClassCastException).

Final Action & Impact

  • DefaultTyping.EVERYTHING + 화이트리스트 적용 이 프로젝트 패키지로 제한한 PolymorphicTypeValidator를 커스텀 ObjectMapper에 활성화해 1차 수정
  • 회귀 발생 및 원인 재규명 EVERYTHING이 Long/String 같은 필드 값에도 @class 태그를 붙이는데, 화이트리스트가 프로젝트 패키지/java.util만 허용해 id: Long 역직렬화 시 InvalidTypeIdException 발생(캐시 히트 경로에서만 재현)
  • 화이트리스트 확장으로 최종 해결 PolymorphicTypeValidator에 java.lang/java.time을 추가해 해결, RedisConfigTest로 캐시 라운드트립 후 타입 검증하는 회귀 테스트 추가

02. 장시간 유지되는 SSE 연결의 DB 커넥션 풀 고갈

SSE HikariCP JPA
Resolved

Root Cause

spring.jpa.open-in-view(기본 true)는 HTTP 요청이 끝날 때까지 DB 커넥션을 붙잡아두는데, 서버 사이드 뷰 렌더링이 없는 이 REST API에서는 애초에 불필요했다. 그런데 streamScheduleEvents(SseEmitter, 장시간 유지되는 스트림)는 요청이 사실상 끝나지 않아 커넥션이 계속 물려 있다가 HikariCP 풀(기본 10개)을 고갈시켰다.

Final Action & Impact

  • open-in-view: false 전환 모든 컨트롤러가 이미 @Transactional 서비스 메서드 안에서 완성된 DTO(record)만 반환한다는 점(지연 로딩 엔티티를 컨트롤러까지 들고 가지 않음)을 확인한 뒤 안전하게 비활성화
  • SSE 연결 증가에도 안정적인 커넥션 풀 유지 REST API 특성상 뷰 렌더링이 필요 없어 부작용 없이 적용, 장시간 연결이 늘어나도 DB 커넥션 풀이 고갈되지 않는 구조 확보

03. ADMIN 전체 조회 캐시가 다른 유저 쓰기에 무효화되지 않던 사각지대

Cache Redis
Resolved

Root Cause

프론트는 항상 userId 파라미터 없이 GET /api/schedules를 호출하는데, ADMIN이 이렇게 조회하면 targetUserId가 null이 되어 "{email}-null-null" 키로 캐싱됐다. evictScheduleCacheForUser()의 "*-{userId}-*" 패턴은 이 "null" 세그먼트에 매치되지 않아, 다른 유저가 일정을 만들거나 지워도 ADMIN의 전체 목록 캐시는 그대로 남아 "삭제해도 새로고침해도 계속 떠 있다"는 리포트로 이어졌다.

Final Action & Impact

  • "-null-" 패턴을 유저별 evict 대상에 포함 어떤 유저의 쓰기든 ADMIN의 전체 목록 캐시를 함께 무효화하도록 evictScheduleCacheForUser()를 수정
  • 재현 기반 검증 Redis에서 실제 stale 키를 재현해 원인 규명 후 ScheduleCacheEvictionTest 2건(create/delete) 추가, 별도 ADMIN/USER 테스트 계정으로 수정 전/후 동작 차이를 curl로 직접 검증
