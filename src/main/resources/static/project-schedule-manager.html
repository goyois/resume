프로젝트 소개

AI 갓생비서는 일정 CRUD, 반복 일정, 만다라트 목표 관리에 Claude 기반 AI 추천 챗봇까지 얹은 개인 스케줄링 백엔드입니다. 인증은 JWT 액세스/리프레시 토큰 로테이션에 Redis 캐싱과 로그아웃 블랙리스트를 더해서 구성했고, 일정이 바뀌면 폴링 없이 SSE로 바로 화면에 반영되게 했습니다. AI 챗봇은 Spring AI(ChatClient)로 Claude를 붙였는데, 텍스트 한 줄 던지고 끝나는 게 아니라 구조화된 형태로 여러 일정을 한 번에 추천하거나 기존 일정 수정까지 제안하고, 대화 맥락도 계속 이어갑니다. 여기에 pgvector 기반 RAG로 사용자의 만다라트 목표나 과거 일정을 참고하도록 해서 조금 더 개인화된 제안이 나오게 했고요. 배포는 AWS(EC2 + RDS + ElastiCache)에 GitHub Actions로 CI/CD까지 직접 구성해서 올렸습니다.

[캐싱] KEYS 명령이 숨겨둔 문제

캐시 무효화 로직에 KEYS 명령을 그대로 쓰고 있었다. 지금 당장은 괜찮아도 블로킹 명령이라, 데이터가 늘어나면 Redis 메인 스레드를 오래 붙잡을 소지가 있었다.

[조회] 흔한 N+1이 여기도 있었다

일정 목록을 DTO로 매핑하는 단계에서 LAZY로 걸어둔 user/category를 그냥 호출해버리고 있었다. 그러다 보니 목록 개수만큼 추가 SELECT가 따라붙었다.

[조회] 인덱스는 있는데 정작 안 맞았다

user_id, category_id에 각각 FK 기반 단일 컬럼 인덱스만 걸려 있어서, 두 조건을 같이 필터링하면 한쪽만 인덱스를 타고 나머지는 row-by-row로 걸러내고 있었다.

TASK과제
[캐싱] 정확하면서도 최소한으로

무효화를 빠뜨리지 않으면서 불필요한 전체 삭제는 막고, 거기에 Redis가 죽어도 서비스는 멀쩡해야 한다는 것까지 - 세 가지를 동시에 만족하는 캐시 전략이 필요했다.

[조회] SQL 한 방, 그리고 숫자로 확인

목록 조회를 SQL 한 번으로 끝내고 싶었고, 실제 사용 패턴(유저는 여러 카테고리를 갖고 카테고리는 여러 유저가 공유)을 그대로 재현한 벤치마크로 인덱스 효과가 진짜 있는지 숫자로 확인하고 싶었다.

ACTION실행
[캐싱] 유저 단위로 타겟팅해서 지우기

update/delete는 findSchedule(id) 시점에, create는 request.userId()로 어차피 소유자를 알 수 있다는 데 착안했다. 해당 유저 관련 키만 패턴 매칭으로 지우는 evictScheduleCacheForUser()를 만들어 전체 무효화를 대체했다.

[캐싱] SCAN·fail-open·TTL로 안전망까지

블로킹 KEYS는 논블로킹 SCAN으로 바꿨다. CacheFailSafeErrorHandler를 붙여서 Redis가 죽어도 그냥 DB 조회로 폴백하게 했고, TTL 5분을 안전망으로 깔았다. ADMIN 전체조회 키("-null-" 패턴)를 evict 대상에서 빠뜨렸던 사각지대도 이참에 같이 없앴다.

[조회] QueryDSL로 갈아엎고 조회 통합

ScheduleRepositoryCustom/Impl을 추가해서 QueryDSL로 user/category를 join하고, @QueryProjection으로 DTO 필드를 SQL 1번에 바로 projection하게 했다. 네 갈래로 흩어져 있던 조회 메서드도 동적 where 조건 하나로 합쳤다.

[조회] 복합 인덱스 추가하고 직접 재보기

Schedule 엔티티에 (user_id, category_id) 복합 인덱스를 추가했다. 감으로 끝내지 않고 5개 카테고리·15명 공유 규모(약 5.7만 건)의 컨텐션을 재현하는 ScheduleIndexPerformanceTest를 짜서 EXPLAIN 실행계획과 응답시간을 같이 재봤다.

RESULT결과
[캐싱] 무효화 범위 최소화, Redis 죽어도 서비스는 유지

전체 삭제에서 해당 유저 캐시만 지우는 구조로 바뀌었다. fail-open 정책 덕분에 Redis에 장애가 나도 API 응답 실패로는 이어지지 않는다.

목록 조회는 이제 항상 SQL 1회로 끝난다. EXPLAIN 기준 옵티마이저 비용이 975 → 251(-74%)로 떨어졌고, 평균 응답도 10.85ms → 9.6ms, 최대 응답은 19ms → 13ms로 편차 자체가 줄었다.

ACTION실행
구조화된 응답 받고, 방어적으로 파싱하기

ChatClient.call().entity(DTO.class)로 title/content/startAt/endAt/categoryId를 구조화해서 받도록 했다. 존재하지 않는 카테고리나 깨진 시각값이 오면 서버가 그냥 null로 비워버리게 방어적으로 짰다. AiResponseCategory(SCHEDULE_RECOMMENDATION/SCHEDULE_UPDATE/GENERAL)로 응답을 먼저 분류해서, 분류에 맞는 등록/수정 UI만 뜨게 했다.

대화가 이어지도록 이력 관리

AiChatMessage로 대화 이력을 DB에 쌓아서 맥락을 유지했다. 요청을 보낼 때마다 최근 대화 요약도 같이 실어 보낸다.

pgvector로 RAG 붙이기

완성된 만다라트 블록과 ±2주 윈도우 밖의 과거 일정을 미리 임베딩해두고, 지금 대화와 의미적으로 비슷한 항목을 few-shot 예시나 컨텍스트로 끼워 넣는다. vector_store 테이블 하나를 docType 메타데이터로 구분해서 같이 쓰는 식으로 구성했다.

호출 제한, 그리고 M1 버전이 던져준 자잘한 버그들

Redis 고정 윈도우 카운터로 ADMIN을 제외한 유저는 분당 5회로 제한했다(Redis 장애 시엔 fail-open). 여기까진 예상한 작업이었는데, M1 라이브러리라 그런지 자잘한 이슈가 계속 튀어나왔다. temperature 필드 때문에 400이 나서 ChatModel 빈을 직접 구성해 그 필드를 아예 빼버렸고, 다중 추천(최대 10개) 응답이 길어지니 기본 max_tokens(500)에 JSON이 중간에 잘려 파싱이 깨지길래 4096으로 올렸다. "오늘 날짜 강제" 로직도 미래 날짜 요청까지 뭉개버리는 회귀를 일으켜서, 모델이 계산한 날짜를 그냥 믿는 쪽으로 바꿨다.

벤치마크 테스트가 CI에 그냥 섞여 있었다

EXPLAIN 실행계획이나 응답시간을 재는 벤치마크 테스트를 일반 테스트와 똑같이 돌리고 있었다. 그런데 CI용 DB는 매번 텅 비어있으니 그 값 자체가 의미가 없고, 실행 시간만 쓸데없이 늘어나는 꼴이었다.

CI가 멈춘 줄 알았는데 알고 보니

CI에는 더미 Anthropic 키를 넣어뒀는데, 이게 인증 실패로 계속 재시도를 타면서 빌드가 멈춘 것처럼 한참 걸리는 일이 생겼다.

TASK과제
변경마다 검증을 강제하는 규칙이 필요했다

변경할 때마다 테스트를 같이 작성하고, 실제로 돌려서 확인한 뒤에만 완료라고 보고하도록 강제하는 개발 하네스가 있어야 했다.

로컬과 CI, 테스트를 나눠야 했다

로컬에서는 성능 벤치마크까지 전체를 돌리되, CI에서는 의미 없는 벤치마크는 빼는 이원화가 필요했다.

ACTION실행
CLAUDE.md에 규칙을 글로 정리해뒀다

"새 로직에는 반드시 테스트를 같이 작성한다", "코드만 읽고 성공했다고 말하지 말고 실제로 실행해서 확인한다", "테스트를 못 돌렸으면 못 돌렸다고 그대로 말한다" 같은 규칙과 [category-N] 형식의 커밋 컨벤션을 문서로 정리해뒀다. 이걸 118개 커밋 내내 일관되게 지켰다.

@Tag로 CI/로컬 테스트 갈라두기

EXPLAIN·응답시간 기반 벤치마크(ScheduleIndexPerformanceTest 등)에 @Tag("performance")를 달아 분리했다. GitHub Actions는 `./gradlew test -PciBuild`로 이 태그만 빼고 돌린다. 그래서 로컬에서는 전체 검증, CI에서는 빈 DB에서 의미 없는 벤치마크를 뺀 회귀 테스트만 빠르게 도는 구조가 됐다.

단위 테스트로는 부족해서 실제로 눈으로 봤다

Mockito 기반 단위 테스트만으로는 안심이 안 됐다. SSE 실시간 반영은 curl로 이벤트 스트림을 직접 찍어보고, Playwright로 새로고침 없이 화면이 갱신되는지도 확인했다. 캐시 무효화 버그도 Redis에서 stale 키를 직접 재현한 다음 curl로 수정 전/후를 비교하는 식으로, 매번 눈으로 확인하는 습관을 들였다.

CI 멈춘 것처럼 보이던 문제도 정리

더미 Anthropic API 키가 반복 재시도를 유발해 CI가 멈춘 것처럼 보이던 부분도 따로 손봤다.

RESULT결과
118개 커밋, 186개 테스트

기능을 바꿀 때마다 회귀 검증이 자연스럽게 따라붙는 구조가 자리를 잡았다. 변경이 쌓여도 이전 동작이 깨지지 않았다는 걸 계속 확인할 수 있었다.

CI는 빠르게, 로컬은 꼼꼼하게

CI는 매번 무의미한 벤치마크 없이 빠르게 돌고, 로컬에서는 성능 회귀까지 포함해서 전체 검증이 가능해졌다.

"통과했다"보다 "확인했다"

테스트가 초록불이라고 바로 끝내지 않고 curl이나 Playwright로 실제 동작을 직접 본 다음에 완료로 보고하는 걸 코드 리뷰 전 단계에서 스스로 지키게 됐다.

SITUATION 상황
세션 기반은 나중에 서버를 늘릴 때 발목을 잡는다

나중에 서버를 여러 대로 늘릴 걸 생각하면, 세션 저장소 없이 동작하는 무상태(Stateless) 인증 구조가 맞다고 판단했다.

토큰 수명, 짧게도 길게도 문제였다

토큰 수명을 짧게 잡으면 자꾸 재로그인해야 해서 UX가 떨어지고, 길게 잡으면 탈취당했을 때 피해 기간이 늘어난다.

로그아웃해도 토큰은 살아있다

JWT는 발급하고 나면 서버가 자체적으로 무효화할 방법이 없다. 그래서 로그아웃을 해도 만료 전까지는 기존 액세스 토큰이 여전히 통했다.

TASK 과제
무상태는 유지하면서 갱신 체계 설계

세션 없이도 로그아웃과 탈취에 대응할 수 있는 액세스/리프레시 토큰 체계를 만들어야 했다.

재발급하면 이전 토큰은 바로 폐기되게

재발급이 일어날 때마다 직전 리프레시 토큰이 자동으로 무효화되는 로테이션 구조가 필요했다.

ACTION 실행
토큰 타입부터 구분했다

JwtUtil에 tokenType claim(ACCESS/REFRESH)을 추가했다. JwtAuthenticationFilter가 ACCESS 타입만 인증에 쓰도록 검증하게 해서, 리프레시 토큰이 Authorization 헤더로 몰래 재사용되는 걸 막았다.

Redis로 단일 세션 로테이션 구현

리프레시 토큰을 refresh:{email} 키(TTL = 잔여 유효기간)로 저장해두고, 재로그인하면 같은 키를 덮어써서 이전 토큰이 자동으로 폐기되게 했다. POST /api/auth/refresh는 서명·만료 검증과 Redis 저장값 일치를 둘 다 통과해야만 access/refresh를 같이 재발급한다. 그래서 탈취된 토큰이 재사용되면 값이 안 맞아서 바로 걸린다.

로그아웃할 땐 두 군데를 같이 지운다

액세스 토큰을 블랙리스트에 올리는 것만으로는 부족해서, refresh:{email} 키까지 같이 지웠다. 이렇게 하면 로그아웃 이후엔 재발급 경로 자체가 막힌다.

프론트에서 자동 재발급, 중복 호출은 막고

401/403이 오면 리프레시 토큰으로 한 번 재발급받고 재요청하도록 했다. 여러 요청이 동시에 만료를 맞으면 재발급 호출도 여러 번 나갈 수 있어서, 진행 중인 refresh Promise를 공유(refreshInFlight)해 중복 호출을 막았다.

RESULT 결과
세션 저장소 없이도 확장 가능한 인증

서버를 늘려도 별도로 세션을 동기화할 필요가 없는 무상태 인증을 확보했다.

로그아웃·탈취 둘 다 막혔다

로그아웃하면 그 즉시 재발급이 불가능해졌고, 탈취된 리프레시 토큰이 재사용되면 정상 사용자의 다음 재발급 요청이 값 불일치로 실패하면서 탈취 사실이 드러난다.

사용자는 이 과정을 전혀 못 느낀다

액세스 토큰이 만료돼도 자동 재발급이 알아서 처리해서, 재로그인 없이 계속 서비스를 쓸 수 있다.

SITUATION상황
[성능] email에 인덱스가 없었다

JwtAuthenticationFilter의 loadUserByUsername부터 각 서비스의 requesterEmail resolve까지, 인증된 요청 하나마다 인덱스 없는 email 컬럼을 최소 두 번씩 조회하고 있었다.

[성능] 리포트 하나 뽑는데 전체 이력을 다 긁어왔다

ReportService의 getStats/getInsight를 보니 범위 제한 없이 유저의 모든 일정을 가져온 다음 메모리에서 걸러내고 있었다. 일정이 쌓일수록, 특히 반복 일정을 많이 가진 유저일수록 매 요청이 느려지는 구조였다.

[성능] saveAll이라고 써놓고 사실은 건건이 INSERT

GenerationType.IDENTITY는 행마다 생성된 키를 바로 읽어야 하기 때문에 JDBC 배치 자체가 안 된다. 그래서 반복 일정이나 만다라트 보드에서 saveAll을 호출해도 실제로는 한 건씩 개별 INSERT를 왕복하고 있었다.

[RAG] 유사도 하한선이 없어서 뭐든 다 끼워 넣고 있었다

VectorStore.similaritySearch에 similarityThreshold를 따로 지정하지 않고 있었다. 기본값이 0.0이라 사실상 무제한 허용인 셈이라, 의미상 완전히 무관한 일정도 "그나마 제일 덜 무관한" topK로 뽑혀서 AI 프롬프트에 그대로 섞여 들어가고 있었다.

[RAG] 나중에 쓸 색인 때문에 지금 응답이 늦어지고 있었다

일정이나 만다라트를 생성·수정·삭제할 때마다 임베딩 색인이 동기로 호출되고 있었다. 이 색인은 나중에 챗봇한테 질문할 때나 쓰이는 건데, 정작 매 쓰기 요청의 응답이 OpenAI API 호출이 끝날 때까지 붙잡혀 있었다.

TASK과제
[성능] 감이 아니라 숫자로 병목을 잡아야 했다

캐시/AI 라인은 이미 다뤘으니, 그 바깥에서 실제로 비용이 나는 지점을 코드에서 직접 찾고 As-Is/To-Be를 벤치마크로 재서 개선 근거를 남기고 싶었다.

[RAG] 검색 품질과 응답 지연, 두 축을 같이 잡기

리트리벌 정확도(무관한 결과를 걸러내는 것)와 쓰기 경로 지연(비동기화)은 서로 다른 문제인데, 이걸 같이 진단하고 풀어야 했다.

ACTION실행
[성능] email에 유니크 인덱스 추가

email은 로그인 식별자니까 어차피 유일해야 한다(이미 애플리케이션 레벨에서 existsByEmail로 검사하고 있었다). 여기 착안해서 DB 레벨 백스톱 겸 유니크 인덱스를 추가했다.

[성능] ReportService 조회 범위를 확 줄였다

searchSchedulesInRange로 이번 기간과 직전 기간만 하나의 bounded 쿼리로 좁혔다. RAG 컨텍스트는 매칭된 소수 id만 따로 타겟 조회하도록 분리했다.

[성능] IDENTITY를 SEQUENCE로 바꿔서 진짜 배치 INSERT가 되게

Schedule/MandalartCell을 SEQUENCE(allocationSize=50)로 바꾸고 hibernate.jdbc.batch_size=50에 order_inserts/updates까지 설정했다. 기존 IDENTITY 시퀀스와 값이 겹치지 않게 별도 시퀀스를 새로 채번해서 안전하게 넘어갔다.

[RAG] 유사도 하한선 0.35, 숫자로 정했다

적당히 값을 정하고 싶지 않아서 실제 OpenAI 임베딩으로 코사인 유사도를 직접 재보고 임계값을 검증했다. 이 값 미만 결과는 VectorStore 단에서 걸러내도록 SearchRequest에 반영했다.

[RAG] 임베딩 색인·삭제를 비동기로

전용 embeddingTaskExecutor를 등록하고 색인·삭제 메서드에만 @Async를 붙였다(검색은 결과를 바로 써야 하니 동기로 남겨뒀다). 트랜잭션 롤백 시 고아 문서가 남을 수 있다는 리스크는 있었지만, 동기로 처리하던 때도 똑같이 있던 문제라 새로 생긴 리스크는 아니라고 판단했다.

RESULT결과
[성능] 세 지점 다 숫자로 확인했다

email 조회는 3.45ms → 0.05ms로 Seq Scan에서 Index Scan으로 바뀌었고, 리포트 조회는 3.85ms → 0.75ms(1,095건 반환이 21건으로 줄었다), 벌크 INSERT는 1,000건 기준 241ms → 147ms(39% 단축)로 나왔다. 시퀀스 값이 실제로 50 배수로 전진하는 것도 직접 눈으로 확인했다.

[RAG] 무관한 결과는 빠지고, 쓰기는 안 막히게

임계값을 적용하고 나니 치과 예약, 회계 보고서 같은 무관한 후보가 실제로 빠지는 걸 확인했다. 임베딩 색인을 비동기로 돌린 덕분에 300ms 지연을 모킹한 기준으로 호출자 블로킹 시간이 310ms → 1ms로 줄었다. 다만 코사인 유사도 순서가 실제 관련도와 어긋나는 구간이 아직 남아있어서, 이 부분은 한계로 남겨뒀다.

01. Redis 캐시 직렬화 버그와 그 회귀

Redis Jackson
Resolved

Root Cause

AiService에서 갑자기 ClassCastException이 터졌다. 캐시 히트 시점에만 나는 걸 보고 Redis 직렬화 쪽을 의심했는데, 파보니 GenericJackson2JsonRedisSerializer(ObjectMapper) 생성자가 기본(no-arg) 생성자와 달리 넘겨받은 ObjectMapper에 default typing을 켜주지 않고 있었다. 그래서 캐시 히트 시 List<ScheduleResponseDto>가 List<LinkedHashMap>으로 역직렬화되고 있었고, DTO 필드를 타입으로 바로 꺼내 쓰던 AiService가 이걸 제일 먼저 걸려 넘어진 것이었다.

Final Action & Impact

  • DefaultTyping.EVERYTHING + 화이트리스트로 1차 수정 이 프로젝트 패키지로 제한한 PolymorphicTypeValidator를 커스텀 ObjectMapper에 켜서 일단 해결한 줄 알았다
  • 근데 곧바로 회귀가 났다 EVERYTHING이 Long/String 같은 필드 값에도 @class 태그를 붙이는데, 화이트리스트는 프로젝트 패키지/java.util만 허용해서 id: Long을 역직렬화할 때 InvalidTypeIdException이 났다. 그것도 캐시 히트 경로에서만 재현되는 골치 아픈 케이스였다
  • 화이트리스트를 넓혀서 마무리 PolymorphicTypeValidator에 java.lang/java.time을 추가해 해결했다. 같은 걸 또 겪지 않으려고 RedisConfigTest로 캐시 라운드트립 후 타입을 검증하는 회귀 테스트도 추가했다

02. 성능·RAG 파이프라인 전수 감사 — 인덱스 누락부터 임베딩 블로킹까지

Performance RAG Async
Resolved

Root Cause

캐시랑 AI 쪽은 이미 손을 봤으니, 그 바깥은 괜찮은지 한 번 더 처음부터 훑어보기로 했다. 코드를 하나씩 따라가 보니 생각보다 많이 나왔다. User.email에 인덱스가 없어서 인증 경로(JwtAuthenticationFilter의 loadUserByUsername + 각 서비스의 requesterEmail resolve)마다 요청당 최소 두 번씩 풀스캔이 나고 있었고, ReportService는 리포트 하나 뽑으려고 유저의 전체 일정 이력을 범위 제한 없이 읽고 있었다. IDENTITY 생성전략은 반복 일정·만다라트 벌크 저장의 JDBC 배치를 아예 막고 있었고, RAG 쪽도 유사도 하한선 없이 무관한 결과를 topK만큼 채워 넣거나 임베딩 색인이 일정 쓰기 요청 스레드를 동기로 붙잡고 있는 걸 확인했다.

Final Action & Impact

  • User.email에 유니크 인덱스 추가 5만 행을 직접 시딩해서 재봤다(UserEmailIndexPerformanceTest). Seq Scan 3.45ms가 Index Scan 0.05ms로 줄었고, 이건 모든 인증 요청 경로에 다 적용되는 개선이었다
  • ReportService 조회 범위를 이번/직전 기간으로만 좁혔다 3년치(1,095건) 일정을 가진 유저를 기준으로 "이번 주" 리포트를 재보니, 전체 조회 3.85ms(1,095건 반환)가 bounded 조회 0.75ms(21건 반환)로 줄었다. RAG 컨텍스트는 매칭된 id만 따로 조회하도록 분리했다
  • IDENTITY를 SEQUENCE(allocationSize=50)로 바꿔 진짜 배치 INSERT가 되게 1,000건 saveAll 기준 241ms가 147ms로 줄었다(39% 단축). 시퀀스 값이 실제로 50 배수로 전진하는 걸 직접 확인해서 배치가 제대로 도는지도 검증했다. 기존 IDENTITY 시퀀스와 값이 겹치지 않게 별도 시퀀스를 새로 만들었다
  • RAG 유사도 하한선(threshold 0.35) 추가 적당히 값을 잡고 싶지 않아서 실제 OpenAI 임베딩으로 코사인 유사도를 직접 재봤다. "이번 주말 등산 코스"를 질의했을 때 "치과 스케일링 예약"(0.2530), "분기 회계 마감 보고서"(0.2389) 같은 결과가 하한선 적용 후 실제로 빠지는 걸 확인했다
  • 임베딩 색인·삭제를 비동기로 돌려서 쓰기 요청 블로킹 해소 전용 embeddingTaskExecutor를 등록하고 색인·삭제 메서드에만 @Async를 붙였다(검색은 결과를 바로 써야 해서 동기로 남겨뒀다). 300ms 지연을 모킹한 기준으로 호출자 블로킹 시간이 310ms → 1ms로 줄었다. 다만 코사인 유사도 순서가 실제 관련도와 어긋나는 구간이 남아있는 건 재보면서 확인한 그대로 한계로 남겨뒀다

03. ADMIN 전체 조회 캐시가 다른 유저 쓰기에 무효화되지 않던 사각지대

Cache Redis
Resolved

Root Cause

"삭제했는데 새로고침해도 계속 떠 있어요"라는 제보를 받았다. 재현해보니 ADMIN 계정에서만 나는 문제였다. 프론트는 항상 userId 파라미터 없이 GET /api/schedules를 호출하는데, ADMIN이 이렇게 조회하면 targetUserId가 null이 돼서 "{email}-null-null" 키로 캐싱되고 있었다. 그런데 evictScheduleCacheForUser()의 "*-{userId}-*" 패턴은 이 "null" 세그먼트를 못 잡는다. 그래서 다른 유저가 일정을 만들거나 지워도 ADMIN의 전체 목록 캐시는 그대로 남아있었던 것이다.

Final Action & Impact

  • "-null-" 패턴도 유저별 evict 대상에 넣었다 어떤 유저가 쓰기를 하든 ADMIN의 전체 목록 캐시도 같이 무효화되도록 evictScheduleCacheForUser()를 고쳤다
  • 재현해서 확인하고 테스트로 남겨뒀다 Redis에서 실제 stale 키를 재현해 원인을 확인한 다음 ScheduleCacheEvictionTest 2건(create/delete)을 추가했다. ADMIN/USER 테스트 계정을 따로 만들어서 수정 전/후 동작 차이를 curl로 직접 확인했다
