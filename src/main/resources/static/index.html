SITUATION 상황
동기 처리 방식의 한계

동기 처리 구조로 인해 사용자의 요청에 대한 응답을 변환이 완료될 때까지 기다려야 함

장애 전파 위험성

변환 처리 장애가 생기는 경우 메인 서버까지 전파됨

트래픽 확장성 저하

도메인 간의 강결합으로 인해 트래픽 급증 시 확장성이 저하됨

TASK 과제
비동기 이벤트 기반 처리 성능 향상

전체 프로세스를 비동기 이벤트 기반으로 전환하여 시스템의 처리 성능(TPS)을 향상시키는 것이 목표

실시간 모니터링 환경 조성

사용자에게 작업 진행 상태를 실시간으로 전달할 수 있는 모니터링 환경 구축

ACTION 실행
비동기 메시지 브로커 도입

무거운 파일 변환 작업을 RabbitMQ를 활용해 비동기로 분리하고, 수동 Ack 및 DLQ(Dead Letter Queue) 설정을 통해 처리 안정성 확보

실시간 상태 전달 아키텍처 구축

Worker 서버에서 Redis Pub으로 진행 상태를 발행하고, API 서버가 이를 구독(Sub)하여 클라이언트에게 SSE(Server-Sent Events)로 실시간 푸시

데이터 정합성 보장

Transactional Outbox Pattern과 Debezium(CDC)을 적용하여 데이터베이스 업데이트와 도메인 이벤트 발행 간의 원자성 확보

RESULT 결과
시스템 처리 성능(TPS) 극대화

이벤트 기반 아키텍처(EDA) 전환 및 비동기 처리를 통해 기존 대비 처리 성능(TPS) 500% 향상

사용자 경험(UX) 및 안정성 개선

실시간 진행률 표시로 사용자 대기 경험을 크게 개선했으며, 도메인 간 결합도를 낮춰 변환 모듈의 장애가 메인 서버로 전파되는 것을 완벽히 차단

SITUATION상황
메모리 초과(OOM) 위험

대용량 문서(PDF) 변환 시 전체 파일을 메모리에 로드하는 기존 방식으로 인해 Heap Memory 부족 및 GC 부하로 인한 시스템 지연 발생

TASK과제
Constant Memory Footprint 달성

파일 크기에 관계없이 일정한 메모리 점유율을 유지하여 대용량 파일 처리 안정성 및 서버 가용성 확보

ACTION실행
스트림 기반 아키텍처 개선

DOM 방식 대신 iText의 Stream 기반 PdfWriter를 도입하여 데이터를 Chunk 단위로 분할하여 순차 처리

파이프라인 데이터 흐름 최적화

InputStream과 OutputStream 파이프라인을 연결하여 디스크 I/O와 메모리 버퍼 간의 데이터 병목 현상 해소

RESULT결과
메모리 절감 및 처리 효율 극대화

기존 대비 메모리 사용량 70% 이상 절감 및 대용량 파일 변환 성공률 100% 달성하여 동시 처리 효율 극대화

SITUATION상황
DB 부하 및 변환 지연 발생

변환 대상 파일의 상태 변화를 감지하기 위해 스케줄러가 DB를 지속적으로 조회(Polling)함에 따라 불필요한 I/O 부하 발생

TASK과제
데이터 정합성 보장 및 결합도 해소

DB와 메시지 큐(MQ) 간의 분산 트랜잭션 없이 데이터 정합성(Atomicity)을 보장하고 서비스 간 도메인 결합도 제거

ACTION실행
Transactional Outbox 패턴 적용

비즈니스 로직과 Outbox 테이블 기록을 단일 로컬 트랜잭션으로 묶어 이벤트 발행의 신뢰성 확보

Debezium(CDC) 연동

데이터베이스의 Bin-log를 실시간으로 캡처하여 변경 감지 후 즉시 메시지 브로커로 이벤트 Publish

RESULT결과
성능 최적화 및 지연 시간 단축

DB 폴링 제거를 통해 커넥션 효율성을 향상시키고 이중 쓰기(Dual-write) 문제를 근본적으로 해결하여 이벤트 발행 지연 최소화

SITUATION상황
메시지 유실 및 자원 고갈 위험

컨슈머(Consumer) 단에서 예외 발생 시 메시지가 즉시 유실되거나, 처리 실패 건이 무한 루프에 빠져 브로커 리소스를 점유할 위험 상존

TASK과제
At-least-once 전달 보장 및 예외 제어

메시지 최소 한 번 전송을 보장하고, 비정상적인 실패 건에 대한 명확한 격리 처리 체계 구축

ACTION실행
수동 승인(Manual Ack) 도입

Consumer Acknowledgement를 Manual 모드로 활성화하여 비즈니스 로직이 완전히 성공한 경우에만 브로커로 Ack 신호 전송

재시도 정책 및 DLQ 라우팅

RetryTemplate을 통해 일시적 오류에 대해 최대 3회 재시도를 수행하고, 최종 실패 시 Dead Letter Queue(DLQ)로 라우팅하여 별도의 에러 로깅 체계 구축

RESULT결과
데이터 무결성 및 자생력 확보

메시지 유실 가능성을 0%로 수렴시키며, 일시적인 장애 상황에서도 유연한 복구 체계를 바탕으로 운영 안정성 및 내결함성 강화

SITUATION상황
서버 자원 낭비 및 사용자 피드백 부재

파일 변환 완료 여부를 확인하기 위해 클라이언트가 지속적인 조회 요청(Short Polling)을 보냄에 따라 서버 CPU 및 네트워크 대역폭 낭비 심화

TASK과제
실시간 상태 가시화 설계

사용자에게 변환 진행률을 실시간으로 Push하여 대기 경험(UX)을 개선하고, 다중 분산 서버 환경에서도 이벤트를 매칭할 수 있는 구조 필요

ACTION실행
단방향 실시간 통신망 구축

SSE(Server-Sent Events)를 통한 단방향 실시간 채널을 구축하여 불필요한 HTTP 오버헤드 최적화

다중 노드 브로드캐스팅 처리

Redis Pub/Sub 아키텍처를 결합하여 워커 노드의 이벤트를 클라이언트의 UUID 및 파일명과 매칭하여 세션에 실시간 전달

RESULT결과
UX 혁신 및 트래픽 절감

상태 조회 트래픽을 90% 이상 대폭 절감하였으며, 사용자에게 즉각적인 진행 상태 피드백을 제공하여 전체적인 서비스 신뢰도 확보

01. 대용량 PDF 변환 시 Worker 서버 OOM 장애 해결

Performance JVM OOM iText7
Resolved

Root Cause

MAT 분석 결과, iText7의 `PdfWriter` 객체가 대용량 파일 전체를 **힙 메모리에 로딩**하여 처리하는 DOM 방식 구조가 원인.

Final Action & Impact

  • Stream 처리로 전환 PdfWriter 대신 Stream 기반의 Chunk 처리 도입
  • 메모리 사용량 70% 절감 Constant Memory Footprint 달성 및 처리 효율 향상
